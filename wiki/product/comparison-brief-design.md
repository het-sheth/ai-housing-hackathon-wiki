# Designing an actionable proposal comparison brief

Contribution: Rushi Patel's September 26, 2026 discussion, consolidated September 27. Proposed design requirements, not an accepted new scope or validated workflow. These refine the [proposal comparison](/wiki/product/proposal-comparison.md).

The brief should help a practitioner decide what to investigate next and whether a proposal change alters that action. Its value must be tested using an actual brief, not inferred from general enthusiasm about the concept.

## Minimum useful content

| Field | Decision supported | Behavior when unknown |
|---|---|---|
| Property identity and jurisdiction | Are these rules and records applicable? | Block parcel-specific conclusions until identity is established |
| Applicant objective and housing outcome | Does either proposal preserve the intended housing benefit? | Request the goal; do not optimize silently for fewer approvals |
| Proposal A/B, version date and status | Are these current alternatives, historical revisions or hypothetical options? | Say status unknown; do not imply both can be built |
| Physical changes | Which input changes could affect a check? | Mark missing dimensions; do not infer plans |
| Changed checks with reasons | What must be investigated differently? | State the needed input or interpretation |
| Persistent constraints | What remains unresolved across both options? | Preserve conflicts and unchecked items |
| Evidence and assumptions | Which statements can support action? | Separate source facts, user assumptions and conflicting records |
| Financial feasibility | Has the economic objective been assessed? | Explicitly unassessed without credible inputs |
| Next action | Who should obtain or review what, and why? | Name the missing prerequisite to assigning an action |

## Proposed comparison behavior

Show the housing outcome separately from regulatory difficulty. A proposal that encounters fewer zoning obstacles can still fail to meet the applicant's needs. User assumptions must not overwrite source conflicts. Every consequential changed check needs a source, applicable date, reason and missing-input state. The export must preserve these alongside both proposals.

Keep legal permissibility, physical/site concerns, process complexity and financial status distinguishable. This design note does not establish a numerical score or satisfy a judging requirement by assertion.

## Acceptance examples for a future prototype

1. Changing a repair proposal to expansion cannot retain an unexplained repair-only conclusion.
2. Unknown lawful use remains unresolved even after favorable user assumptions.
3. A persistent assessment/permit conflict appears in both proposals and the exported brief.
4. Unsupported geography and unavailable sources produce explicit limitations, not a clean result.
5. A hypothetical alternative is visibly labeled and cannot acquire approval status through comparison.
6. A reduction in housing output stays visible even if fewer checks apply.

These are proposed evaluation criteria, not claims of implemented or passing tests. The next useful feedback identifies a misleading statement, a missing decision-relevant fact or an actionable next step. See [open questions](/wiki/product/open-questions.md) for the broader unresolved scope.
