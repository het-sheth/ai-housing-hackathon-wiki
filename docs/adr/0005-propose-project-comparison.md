# ADR 0005: Propose a project comparison workflow

- Status: Proposed
- Date: 2026-09-26
- Decision owner: Het and Rushi
- Approval evidence: Het requested adding findings to the wiki and proposing the idea to Rushi. This approves documentation, not the product or implementation.
- Supersedes: None

## For Humans

### Decision

Evaluate one City of Pittsburgh parcel with two explicitly supported housing proposals, explain the rule checks that change, and export a cited next-action brief. Primary user hypothesis is a small nonprofit developer's project lead. See `wiki/product/proposal-comparison.md`.

### Why

A static parcel brief substantially overlaps documented competitor capabilities. SME guidance supports executing one feasibility dimension well. One manual parcel join is demonstrated; scope-dependent utility remains unvalidated.

### Tradeoffs

Comparisons may be useful but require more reliable rules and proposal inputs than a static brief. Keeping finance unassessed limits claims but avoids unsupported estimates.

## For Agents

### Context and evidence

See the proposal, September 26 evidence update, presentation excerpts and Lanark worked example. Do not treat source access, SME encouragement or one data test as demand, approval or market novelty.

### Alternatives considered

Static site brief; project comparison; combined zoning and full financial modeling. Recommend testing project comparison before selecting it.

### Consequences and constraints

No app code is authorized by this ADR. No framework selected. Keep scoring components and coverage separate. Full financial modeling and broad persona-specific interfaces are deferred in the proposal.

### Revisit when

Het and Rushi review the proposal, one rule trace succeeds or fails, and a practitioner evaluates whether comparison changes a real decision.
